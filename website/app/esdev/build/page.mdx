# esdev build

```sh
esdev build server.ts                          # → dist/server.js
esdev build src/app.ts --out=dist/app.js --minify
esdev build styles/app.css --minify            # → dist/app.css
```

One entry, one file, ES modules out. `runtime:*` imports are left for the
runtime to serve, and **CommonJS dependencies are converted on the way in**.

For a stylesheet entry, the output is CSS rather than JavaScript: its default
is `dist/<entry>.css`. It follows local `@import`s before it writes. See
[Browser builds](/esdev/build/browser#stylesheets-and-css-modules) for CSS
entry, asset, CSS Module, and library usage.

## The CommonJS answer

`esrun` runs ES modules only, while a large share of npm still ships CommonJS.
The bundler converts CJS to ESM on the developer's machine so the deployed
artifact remains the text that was reviewed:

```sh
esdev build server.js         # a CJS dependency goes in
esrun dist/server.js          # ordinary ESM comes out
```

`esdev test` and `esdev <file>` convert a CommonJS package as they load it, so a
test needs no build step. See [Imports](/esdev/test/imports#commonjs-packages).

## A shorter deploy line

An unbundled program needs `--allow-imports`, because the loader walks
`node_modules` at runtime. A bundle that stays one file has no imports left to
resolve:

```sh
esrun --allow-imports --allow-listen=8080 app.js  # unbundled
esrun --allow-listen=8080 dist/app.js             # bundled
```

A bundle that **splits** keeps the grant. A dynamic `import()`, and a module
named with `new URL(…, import.meta.url)`, each become a chunk of their own, and
loading one at run time is an import the runtime must resolve:

```sh
esrun --allow-imports --allow-listen=8080 dist/app.js  # code-split
```

The build is a security step, not only a packaging one.

## Options

| Flag | |
| --- | --- |
| `--out=<file>` | Where to write it (default `dist/<entry>.js`, or `dist/<entry>.css` for a stylesheet) |
| `--minify` | Minify the output |
| `--conditions=<list>` | Extra `exports` conditions, comma-separated; these add to `import`, `default`, `worker` |
| `--define=<name>=<value>` | Replace a name at build time; `process.env.NODE_ENV` defaults to `"production"` |
| `--inventory=<file>` | Write what the build shipped as a draft [dependency policy](/docs/security/dependency-policy): each package's version and `h1:` hash |
| `--alias=<name>=<to>` | Rewrite a specifier before it resolves; repeatable |
| `--sourcemap[=<kind>]` | A `.map` beside the output, or `=inline`, or `=hidden` |
| `--target=<name>` | Build one target of the project's `esdev.json` |
| `--config=<path>` | Read this project file instead of `./esdev.json` |
| `--lib`, `--format`, `--no-types`, `--dts-bundle`, `--css-urls` | A library build ([Library builds](/esdev/build/library)) |

`esdev build` with no entry builds the targets `esdev.json` describes, each flag
applied to every one of them ([Flags on a project build](/esdev/build/project#flags-on-a-project-build)).
Naming an entry builds that one, with the project's `jsx`, `resolve.alias` and
`plugins`.

## What the application build guarantees

| | |
| --- | --- |
| **`runtime:*` stays external** | It is served by the runtime and has no file behind it. |
| **ESM output** | The runtime has no other module system. |
| **`process.env.NODE_ENV` is defined** | Packages branch on it before doing anything, and there is no ambient `process` global. It describes the build; where the bundle runs is [`RUNTIME_ENV`](/docs/deployment/runtime-env), read at run time and never defined here. |
| **The `worker` condition is asserted** | Packages can select their Web-API build. |

`--conditions` adds rather than replaces, so asking for one more cannot silently
cost the `worker` condition. A dynamic `import()` emits a content-hashed chunk
beside the entry.

A module named with `new URL("./path.js", import.meta.url)` is built as a
content-hashed chunk of its own, and the URL is rewritten to point at it. That
is how a `Worker` finds its entry in the output, and how a durable worker's
shards find the module that defines their classes:

```js
new Worker(new URL("./resize.worker.ts", import.meta.url));
configure({ shards: "auto", module: new URL("./workers.js", import.meta.url) });
```

Only a literal path to a JavaScript or TypeScript module, with
`import.meta.url` as the base, is built this way. A literal path to any other
file is [copied into the output](/esdev/build/browser#files-named-by-url), and
a computed path is left as written.

The bundler's warnings are printed as the build runs. The one to act on is an
import it could not resolve: the bundle keeps it as an import and the build
succeeds, but the program fails where it is deployed, so the warning names the
file and the line.

## Dependency policy

A project whose `esdev.json` names `build.importPolicy` has every build held to
it: each module read into each bundle, for every target and the builds
`esdev start` makes. How to adopt one is on
[Dependency policy](/docs/security/dependency-policy); the rules of the file are
these.

```json
{
  "allow": [
    "./src",
    "@acme/*",
    "left-pad",
    { "package": "zod", "version": "3.23.8", "integrity": "h1:…", "reason": "input validation" }
  ],
  "deny": ["aws-sdk"],
  "unlisted": "error"
}
```

- **An entry beginning with `.` or `/` is a path** covering its subtree,
  relative to the policy file; anything else is a package name. A module
  matches if either kind names it, so a path entry pointing into
  `node_modules` governs what is there.
- **`"@scope/*"` names every package in a scope.** It is the only pattern; `*`
  anywhere else is an error.
- **An object entry** names a package with an optional `version` (checked
  against the installed `package.json`), `integrity` (Go's `h1:` hash of the
  installed directory) and `reason` (for the review). Unknown keys are an
  error. Several entries may name one package, one per approved copy.
- **`deny` wins over `allow`**, and a denied package fails the build in every
  mode, as does a copy whose version or files differ from every entry for it.
- **`"unlisted"`** is `"error"` (the default) or `"warn"`, and says what
  happens to a package `allow` does not name. Without `allow` nothing is
  unlisted, and `"unlisted"` is an error.
- **Omitting `allow`** permits everything not denied; `"allow": []` and an
  unknown key are errors.
- **Matching is on the resolved, canonical path**, so a symlink cannot name its
  way in and a pnpm store path is still its package. A package entry covers
  that package's own files; a nested `node_modules` copy is named in its own
  right.

A refusal lists everything refused and writes nothing. `--inventory=<file>`
writes what a build shipped as a draft policy, and `build.subresourceIntegrity`
adds `integrity` attributes to the tags a release HTML build writes.

## Source maps

```sh
esdev build src/server.ts --out=dist/server.js --sourcemap
```

Source maps are off unless asked. The available forms are:

| Option | Result |
| --- | --- |
| `--sourcemap` | A `.map` beside the output, pointed at by the bundle |
| `--sourcemap=inline` | A data URL in the file itself |
| `--sourcemap=hidden` | Written, with nothing pointing at it — useful for an error reporter |
| `"sourcemap": true` | The same setting per target in `esdev.json`; `"inline"`, `"hidden"` and `false` are also supported |

A map's `sources` are relative to the map, so a deployment can be copied
anywhere with its sources and still resolve them. The map names nothing about
the machine that built it.

`esrun` remaps printed stack traces through the map, while `error.stack` inside
the program remains the engine's original value.
