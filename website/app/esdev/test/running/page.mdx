# Running and isolating tests

`test.only` runs that case and skips the rest; `describe.only` does it for a
group. What did not run is counted and said out loud:

```text
  only: 27 other tests did not run
  1 passed, 0 failed, 27 skipped
```

That line is the point. A `.only` left in a commit otherwise looks exactly like
a suite that got faster, and a skipped case missing from the report is the same
failure as a case that quietly never ran.

## Filtering by name

`-t` runs only the tests whose full name matches a regular expression. The full
name includes the `describe` groups, joined with ` > `. `--test-skip-pattern`
leaves out the tests that match:

```sh
esdev test -t=auth                        # every test under "auth", in every file
esdev test "-t=auth > logs (in|out)"
esdev test -t=auth --test-skip-pattern=slow
```

The value is attached with `=`, as for every esdev flag. Tests left out are
counted as skipped and named on a line of their own, like `.only`:

```text
  filter: 12 other tests did not match
  3 passed, 0 failed, 12 skipped
```

A group with no selected tests does not run its `beforeAll`. Path filters
(`esdev test auth`) choose files; `-t` chooses tests within them, and the two
combine.

## One process per file

A test suite is where isolation matters most. A file that wedges, exhausts its
heap or calls `exit()` must not decide the fate of the others, and a global left
behind by one must not be visible to the next. Each file gets its own process —
the prelude snapshot makes that cheap.

`--file=<path>` is what a child is invoked with, and is equally a supported way
to run one file by hand.

Files run **in parallel** — the machine's parallelism, at most 8, since every job
holds a V8 heap. Each file's output is held and printed whole when it finishes,
so two suites never interleave line by line.

```sh
esdev test                  # all of them, in parallel
esdev test db --watch       # the files whose path contains "db", again on every save
esdev test --jobs=1         # one at a time, writing straight to the terminal
```

`--jobs=1` is the run to reach for when a test is hanging and you want to watch
it happen. `--watch` re-discovers files every pass, so a test you are about to
write is one the watcher will find.

## Sharing one runtime

For a suite whose startup and repeated imports cost more than its tests, opt
out of the process boundary:

```sh
esdev test --isolation=none
```

All selected files then run serially in one process. Their V8 heap, globals and
ES-module cache stay alive, so a shared dependency evaluates once for the run.
Likewise, a `--setup` module evaluates once rather than once per file.
That is a performance mode, not an isolation mode: a global or mock left by one
file reaches the next, `exit()` or a crash ends the whole run, and a hanging
file cannot be stopped independently. `--jobs`, `--timeout`, and the per-file
JSON reporter are unavailable with it.

The default, `--isolation=process`, retains the process-per-file behavior.

## Rehearse the production grant

By default each file runs with every capability, the way `esdev` runs
anything. That is the loop you develop in — and it is wider than what
production grants, so a path the suite covers can pass here and die there with
`NotAllowedError`.

The permission flags narrow each file's run to a production-shaped grant, so a
covered path meets its deployment's capabilities before deployment:

```sh
esdev test --deny-all --allow-read=./data --allow-env=DATABASE_URL
```

`--deny-all` takes everything; `--allow-*` grants back what the suite needs —
the same flags, resolved the same way, as a run. `--deny-<name>` subtracts a
single capability instead: `esdev test --deny-net` fails a suite the moment
anything in it touches the network. A combination that cannot exist
(`--allow-env=X` without `--deny-all`) is refused before anything runs, not
once per file.

Grant what the harness needs too, not just the program: snapshot writes need
`--allow-write`, helper imports `--allow-imports`. The flags travel to every
child, and `--isolation=none` resolves them for its single process. They are
flags only, never `esdev.json` keys — a rehearsal decides a single run. Run
with none of them and nothing changes: full grant, full fidelity, exactly as
before.

## The file is the entry, unaltered

It keeps its own path, its module resolution, its relative imports and its
TypeScript — and nothing is added to it. What runs is byte for byte the file on
disk, so a failing assertion names the line you wrote because it *is* the line
you wrote.

A test file is an ordinary module, so running one directly works and reports
the same way:

```sh
esdev app.test.ts
```

## An unhandled rejection

Fails the test it surfaced in. A test that expects one claims it:

```js
addEventListener("unhandledrejection", (event) => event.preventDefault());
```

A listener that does not call `preventDefault()` leaves it unhandled, as in a
browser.

## A test that never finishes

It is reported as a **failure**, not a hang:

```text
  FAIL never finishes
    the test never finished — it is waiting on something that never happened
  3 passed, 1 failed
```

The cases queued behind it are reported as never started, so the report points
at the one that is stuck.
