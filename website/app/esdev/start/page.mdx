# esdev start

```sh
esdev start
```

It is [`esdev build`](/esdev/build) on a loop. A dev build differs from a
release build in four ways and no more: `process.env.NODE_ENV` is
`"development"`, nothing is content-hashed, the browser bundle is built so
a module can be replaced in place — and it is written under the dev
directory (`.dev` by default) rather than where `esdev build` deploys.

The server it runs gets `RUNTIME_ENV=development` unless your shell sets one,
so [`environment()`](/api/process#environment-where-the-program-is-deployed)
reports where it runs; see [The RUNTIME_ENV convention](/docs/deployment/runtime-env).

On a change: rebuild, restart the server if its bundle moved, and patch the
page — or reload it if nothing accepted the change. A change that leaves what
the page loads as it was leaves the page alone: a new file nothing imports, or
an edit to server code alone, such as a loader or an API route — the server
restarts and the page keeps its state, and is told with
[`esdev:server-update`](/esdev/start/hmr#when-the-server-restarts). Read the
details in [Hot module replacement](/esdev/start/hmr).

## What it prints

A banner once it is listening *and* built, then one line per save that
changed the output — nothing else. Build reports and errors go to stderr, so stdout stays the program's:

```text
esdev <version> — ready in <duration>

  →  Local:   http://localhost:5173/
✓ hot-swapped <count> modules in <duration>
✓ reloaded in <duration>
✓ restarted server in <duration>
```

Beside the web entry, each server is listed with its port; a project with one
server and no web entry names that server's URL. A failed build prints its error; the loop keeps running, and the
next save gets its own line. See [Build failures](#build-failures) for browser
errors and output behavior.

## What runs: `dev.servers`

`dev.servers` lists the project's services, one entry each, on the ports they
use — the same topology production has. What an entry is follows from the
target it names (its own name, unless `target` says):

```json
"dev": {
  "servers": {
    "web":    { "port": 5173, "proxy": { "/api": "api" } },
    "api":    { "port": 3000 },
    "worker": { "target": "jobs", "after": ["api"] }
  }
}
```

| The target is | esdev |
| --- | --- |
| **An HTML target** | Serves its dev build on that port, with an `index.html` fallback for client-side routes, the [update channel](#the-update-channel) and the [gateway's routes](#the-gateway-proxy). Default port 5173 |
| **A server target** | Runs its output as a child process and restarts it when it changes. Default: a free port |

Every project that starts has the key — a frontend too, so a second service is
one more entry:

| Project | `dev` |
| --- | --- |
| A frontend (a static site, an SPA) | `{ "servers": { "web": { "port": 5173 } } }` |
| One server — an API, or a full-stack app whose server renders its pages and answers `/api` itself | `{ "servers": { "server": { "port": 3000 } } }` |
| A frontend, its API and a worker | the example above |

### A server entry

esdev runs it with esdev's normal development permissions and restarts it with
a `SIGTERM` — the graceful stop production gets, so a request in flight when
you save is answered rather than dropped. Put production grants on the `esrun`
command that deploys the built program.

The server reads `PORT`. Its `port` is the one it is given; if that is in use,
esdev chooses a free one, sets it in `PORT` and says so. `--port=<n>` pins the
one entry's port, which must then be free.

| Key | Meaning |
| --- | --- |
| `target` | The build target it runs. Default: the entry's name |
| `port` | The port it is given in `PORT`. Busy or absent, a free one is |
| `env` | Environment for this server only |
| `args` | Arguments for the program |
| `after` | Servers that must be listening before this one starts |

Each save restarts only the servers whose build output changed, stopping the
ones that depend on them first. A server's errors reach the page under its name
(**Server error: worker**) when there are several. A server that binds no port,
such as a worker, is not waited for unless something names it.

**It is the same build production runs, in development profile.** No dev
server stands in for it, nothing wraps it, and there is no second code path
that exists only on your machine. What differs is only where its bytes land:
every target output is mirrored under `.dev/` (`dist/server.js` is rebuilt
as `.dev/dist/server.js`), so a save never overwrites the deployment. Run
[`esdev build`](/esdev/build) again before deploying — `dist/` is only ever
a release build now.

```json
"dev": { "outDir": "tmp-dev" }
```

names another directory for the loop's builds. It must stay inside the
project and clear of every target's `out` and `outDir`; anything overlapping
is refused when the file is read.

### The web entry

The entry naming an HTML target is served by esdev, from the dev build of that
target. It takes `port` and `proxy`; `env`, `args` and `after` are a server's.
One entry serves a project's pages.

## Build failures

```text
esdev: src/App.tsx: Unexpected token
```

The running server keeps serving when a rebuild fails. The rebuild happens
before the server is stopped, so it also answers while the build runs.

The error is sent to the browser and shown in an overlay until a successful
update clears it. A page that opens or reconnects during the failure receives
the current error too.

When the first build fails, esdev prints `the build failed; fix it and save`
instead of the banner, and the banner once a save fixes it. Until then a page
request with nothing built to load is answered with the error, status 500, on
a page that reloads itself when the build succeeds. A missing asset is still a
404.

Development outputs are written in place: a failed build may already have
updated some files. The loop's output directory is separate from the release
output. [`esdev build`](/esdev/build/project#safe-output-replacement) stages
release outputs before replacing them.

## Server errors

When the server a project runs fails a request, or crashes, the error reaches
open pages in the same overlay, under **Server error**:

```text
runtime:http: GET /orders/42 failed (trace 4bf92f3577b34da6a3ce929d0e0e4736)
RangeError: the ledger exploded
    at …
```

The terminal shows it once, from the server. An error the server's own
[`onError`](/api/http#handler-errors) answers is handled and is not shown. The
next update clears the overlay; a page that opens later does not receive it,
since the request it belonged to is over.

esdev and the server are linked for the life of the server. A restart asks the
server to drain in-flight requests within `--shutdown-grace` on every platform,
Windows included, and a server whose `esdev start` is killed stops too rather
than holding its port.

## The update channel

Every built document gets a WebSocket to `/@esdev/hmr` on esdev's port, at
the page's own host — so a phone on your network, or a forwarded port, gets
updates as `localhost` does. It acts on a module patch, stylesheet swap,
or reload. It is esdev's endpoint rather than your application's, so nothing
dev-only reaches your source and the file you edit is never written to.

An update is sent **after** a restart finishes. The client reconnects on its
own, backing off to a 5 s ceiling, because a restarted dev server is ordinary.
The port is written into the document when it is built, so this works while the
endpoint keeps the same port. If you stop and start esdev again and its
unpinned endpoint chooses a different port, reload the page; the old document
cannot discover that new endpoint. For a frontend project, use `--port=<n>` to
pin the endpoint.

esdev's listeners — the web entry's and the update channel — are on loopback.
`esdev start --host` opens them to the network, for a phone or a container;
forward the update channel's port too, which the banner names. A server's own
binding is its `serve()` call, as in production.

## Options

| | |
| --- | --- |
| `--port=<n>` | The port of the one `dev.servers` entry |
| `--host` | Open esdev's listeners to the network rather than loopback |
| `--no-hot` | Reload the page instead of patching changed modules |
| `--config=<path>` | Read this instead of `./esdev.json` |
| `--allow-read=<paths>` | Also watch explicitly granted read paths |
| `--shutdown-grace=<ms>` | How long the server may drain on a restart |
| `--tls-ca=<file\|bundled>` | The CAs the server and an `https` [proxy](#the-gateway-proxy) target are verified against, as [esrun's](/api/cli#tls-trust); repeatable |
| `--tls-crl=<file>` | CRLs they are checked against, as [esrun's](/api/cli#tls-trust); repeatable |
| `--proxy=<url>` | The server's outbound proxy, as [esrun's](/api/cli#outbound-proxy). Default: `HTTPS_PROXY`/`HTTP_PROXY` |
| `--no-proxy=<list>` | Targets it reaches directly, as [esrun's](/api/cli#outbound-proxy). Default: `NO_PROXY` |

```json
"dev": { "servers": { "server": { "port": 3000 } }, "watch": { "targets": ["server", "web"], "paths": ["./config"] }, "outDir": ".dev" }
```

Beside `servers`, these `dev` settings control what the loop rebuilds and
watches:

- `watch.targets` selects targets to rebuild. If omitted, esdev rebuilds every
  target except `"then": "run"` steps, which run only in `esdev build`. A
  target a server entry runs is always built. List a step here to run it on
  every save.
- `watch.paths` adds watched paths, resolved relative to `esdev.json`.
- `outDir` is the [loop's own output directory](#a-server-entry).

## The gateway: `proxy`

A split app — the frontend on one port, its API on another — often reaches the
API through a gateway in production: nginx, an ingress or a host's rewrites
send `/api/*` to it, so the page calls `fetch("/api/users")` on its own origin,
with cookies and no CORS. The web entry's `proxy` is that gateway in
development, written as production's is:

```json
"dev": {
  "servers": {
    "web": { "port": 5173, "proxy": { "/api": "api", "/legacy": "http://localhost:8080" } },
    "api": { "port": 3000 }
  }
}
```

A request whose path starts with a prefix goes to its target, the longest prefix
first; everything else is served from the build. A target is a server entry's
name — reached at whatever port it has now, keeping the page's `Host` — or a
URL esdev does not run, which sees its own `Host` with the page's in
`X-Forwarded-Host`, and has its path prepended (`"http://localhost:8080/v1"`
receives `/v1/api/users`). Bodies, streamed responses, server-sent events and
WebSocket upgrades pass through as they are. An `https` target is verified like
`fetch` verifies one.

While a server entry restarts, a request for it waits until it listens again,
as a production gateway's health check would, and a `GET`, `HEAD` or `OPTIONS`
the old process closed without answering is sent to the new one. A target that
does not come back within 10 s answers `502` with why.
[`esdev preview`](/esdev/start/preview) runs no servers, so there only URL
targets apply.

`proxy` is on the web entry only: a server's routes are its own code. A project
whose page calls its API cross-origin (`PUBLIC_API_URL`) needs none.

## Targets only the dev loop builds

A target under `dev.targets` is built and run by `esdev start` and never by
`esdev build`, so nothing it writes reaches a deployment. A static site uses one
to render its pages on a server while you develop, as the prerender step will:

```json
{
  "build": { "targets": {
    "web":      { "entry": "index.html", "outDir": "dist" },
    "site-ssg": { "entry": "ssg.js", "out": ".ssg/ssg.js", "then": "run" }
  } },
  "dev": {
    "targets": { "render": { "entry": "src/dev-render.js", "out": "devserver/render.js" } },
    "servers": { "render": { "port": 3000 } }
  }
}
```

| | |
| --- | --- |
| **Same keys** | A dev target takes what a build target takes, except `then` — nothing runs after a build that never builds it |
| **Its own name** | A name is in `build.targets` or `dev.targets`, not both |
| **Named by the loop** | `dev.servers.<name>.target` and `dev.watch.targets` may name one |
| **Never released** | `esdev build` leaves it out, and refuses `--target=` naming it; `esdev preview` never serves it |

## What is watched

`esdev start` watches the project root, every path under `dev.watch.paths` or
passed with `--allow-read`, and the build inputs those paths may contain. The
dev directory is always excluded, which covers every target
output at once since the loop mirrors them all underneath it — so a build
cannot trigger itself. A directory the project's root `.gitignore` names is
not watched at all — `node_modules` and `dist` in every template — and neither
is `.git`; other directory names are not hardcoded exclusions. An edit to
`.gitignore` applies while the loop runs, and a directory created later is
watched from when it appears.

That includes modules and the things a build consumes that a run does not:
`index.html`, stylesheets, images and fonts. An explicit allowed path is both
part of the watch list. An unscoped `--allow-read` grants access but does not
identify a finite directory to watch.

For the standalone command's narrower rules, see [Watch mode](/esdev/watch).
