# Internals: archives

What `runtime:archive` does below the API: what it refuses, what it holds in
memory, and how a file source is read without buffering the archive.

## The codecs

Tar and zip are read and written by the `tar` and `zip` crates. Both are safe
Rust, and the zip build enables only the deflate decoder, not the encoders a
program could reach. Gzip is flate2, which the runtime already carried for
`CompressionStream`.

The layers above the codecs are ours: the format sniff, path validation,
layout checks, the decompression budget, and the deterministic writers. That is
where an archive stops being bytes and becomes a set of names the filesystem
may receive.

## Format detection

The format is read from the leading bytes: gzip's `1f 8b`, zip's local, empty
or spanned signature, and everything else is tar. A name or extension is never
consulted. An input that claims to be a zip but starts like a tar is handled as
a tar, and if it is not one it fails as a tar.

## Validation before use

Every entry is validated as it is read, and the eager APIs finish a full layout
check before returning. Each path must be:

- relative, slash-separated, valid UTF-8;
- no empty component, no `.` and no `..`;
- no backslash and no drive letter;
- free of duplicates and file/directory collisions, tracked as entries arrive;
- on Windows and macOS, not differing only by ASCII case from an earlier path,
  because the filesystem would merge entries the archive treats as distinct.

Tar links and special types, zip symlinks, encrypted zip entries, and zip
compression other than Stored and Deflated are refused. A directory entry that
carries data is malformed and refused.

Refusal is the design: an archive is never rewritten into a safe-looking one.
Dropping a `..` component or skipping a link would silently change what the
caller unpacks, and code that relies on the difference would be wrong in a way
nothing reports.

## Bounds

Two limits apply, `maxEntries` and `maxBytes` (the uncompressed total). They are
checked twice:

1. from the declared sizes in tar headers and the zip central directory, before
   any entry data is allocated — and, for zip, from the end record before the
   central directory is parsed, because that parse allocates its index;
2. from the bytes a decompressor actually yields, so a header that understates
   its size cannot walk past the budget.

A gzip stream has no declared total to trust, so its decompression is bounded
by `maxBytes` plus a per-entry allowance for tar headers. Over either limit is a
`RangeError` with `ERR_ARCHIVE_TOO_LARGE`.

Listing and single-entry reads do not materialize entries they do not return:
zip metadata comes from the central directory and tar headers are read in order.
`entries()` therefore costs a pass over headers, not a pass over contents, and
the async iterator yields those headers one at a time instead of collecting an
array. A tar.gz entry is reached by decompressing through its predecessors, but
those bytes are discarded as they are skipped rather than retained.

## File sources are streamed

`file()` is opened through the jailed `SyncFileSystem`, which can seek and read
on demand. The fd is opened once and shared by every reader; each reader keeps
its own position and seeks and reads under a lock. The handle remains attached
to the same file if its path is renamed or removed, but it is not an immutable
snapshot if another process writes to that file.

The source is never read into a single buffer: `for await` yields metadata one
entry at a time, `files(filter)` reads only the entries the filter selected,
`ArchiveEntry.stream()` pulls decompressed chunks through a bounded channel.
Extraction writes chunks into a temporary directory, so memory is bounded by
the channel's few chunks and the paths needed for collision checks, not by the
archive's size. Staging uses temporary disk space up to the uncompressed output
size. A zip parser still builds its central-directory index, which `maxEntries`
bounds.

A provider with no synchronous filesystem falls back to reading the file once
through `FileSystem`; that is the best its whole-file seam can do. `bytes()`
also allocates the whole archive, because returning it is the operation.

## Why extraction stages before it writes

`extract()` first scans metadata to check the destination paths for existing
symlinks. It then decodes the archive once into a temporary directory, checking
entry paths, limits, data lengths, zip CRCs and the gzip trailer while it
streams. It checks symlinks again using the paths from the staged archive, then
copies staged files into the destination. The metadata scan and extraction use
the same open file handle, but in-place changes made during extraction are
visible to that read.

If decoding or validation fails, no staged entry is copied to the destination.
The temporary directory costs disk space proportional to uncompressed output.
An I/O error while copying staged files into the destination can still leave
partial output; the staging guarantee covers archive decoding and validation,
not failures during the final filesystem writes.

## Determinism

A build sorts entries by path, writes `0:0` ownership, `0644` files and `0755`
directories, and uses timestamp `0` unless an entry supplied `lastModified`.
Zip's default options depend on whether its time feature is enabled in the
dependency graph — `self_update` enables it — so the writer sets the timestamp
and the system explicitly rather than inheriting a default that could change
between builds. The same entries therefore produce the same bytes, which is what
lets an archive be hashed or cached.

Gzip's header mtime is likewise not the clock: flate2 writes a zero mtime.

## Where the work runs

Metadata scans run on the embedder's `TaskSpawner` (tokio's blocking pool in
`esrun` and `esdev`), inline when there is none. File reads and gzip
decompression run on a dedicated archive worker thread; the writer side awaits
the bounded channel, and extraction writes through the `FileSystem` provider
one chunk at a time.

## Not here

7z, rar, brotli and zstd; passwords; selective extraction (read an entry and
write it yourself); preserving ownership, modes or arbitrary timestamps from an
input archive; and appending.
