# Internals: images

What `runtime:images` does below the API: where the work runs, what bounds
its memory, and what it costs against `Bun.Image`.

## The engine

The module is a thin layer over [otf-pixels](https://crates.io/crates/otf-pixels),
a pure-Rust image engine with its own codecs. There is no C library and no
platform backend, so every format decodes and encodes the same way on every
operating system, and a given input and pipeline produce byte-identical output
everywhere.

## Where the work runs

A chain is recorded in JavaScript as a list of steps; nothing crosses to the
host until a terminal. The terminal sends the source, the steps and the output
in one call, and the host runs the pipeline on the embedder's blocking pool
(tokio's, in `esrun` and `esdev`). The event loop keeps running meanwhile.

Inside a run, tiles are evaluated in parallel on one scheduler that the whole
process shares, workers included. Concurrent pipelines share its threads
rather than each starting a pool of their own.

Nothing is held between calls: there is no image handle to free, and an image
passed to a worker is plain data.

## Stopping a run

A run occupies a pool thread until it finishes, and a thread cannot be stopped
from outside, so the run stops itself. A terminal given a signal files a
cancellation flag with the host for exactly as long as the call lasts; an
abort raises it, and the run checks it before each tile, each decoded row,
inside every buffering codec's loops, and between frames. A chain's `timeout`
is the same flag with a deadline, counted from the terminal call, so the time
spent reading a `file()` and waiting for a free thread is inside it.

How soon a run stops is one unit of that work away: a tile of the most
expensive step, or a codec block. Cheap steps stop at once; a large blur
kernel, whose every tile is costly, stops after that tile. Without a signal
or a timeout there is no flag, and nothing is checked.

## Memory

Opening an image reads its header only. `maxPixels` is checked there, so an
image that declares more pixels than allowed is refused before any pixel
memory exists.

Pixels are pulled through the pipeline in tiles, so a resize of a large
baseline JPEG, TIFF or non-interlaced PNG holds a band of the image rather than
all of it. WebP, AVIF, GIF, JPEG XL, progressive JPEG and interlaced PNG have
no streamable prefix and are buffered whole by their decoder. The encoded input
is held in full: a `file()` is read into memory before it is decoded.

Two steps break the streaming. `trim` cannot know its output size until it
has seen the pixels, so the chain before it runs when the pipeline is built and
its result is held whole; a `resize` placed before it keeps that result small.
A progressive JPEG output holds the image's quantized coefficients, two bytes
per sample, until the last scan is written, where baseline streams.

An animation is held in memory compressed, and each pass over its frames
decodes it afresh: one frame at a time is in pixels, and each frame's tiles
are dropped once it is written. Opening one checks Pixels' animation limits
(10,000 frames, 2³² pixels across every frame) before any frame is decoded.
`stackFrames()` holds the whole sheet, as `trim` holds its input.

A `composite` overlay is a pipeline of its own, joined to the base's graph.
Its encoded bytes cross to the host with the base's, and a `file()` overlay is
read in JavaScript through `runtime:fs` before the call, so the op that runs the
pipeline only ever reads the file its own source names.

## Speed

The [benchmarks](/docs/benchmarks#images) measure `runtime:images` against
Bun, Deno and sharp. Bun's codecs are libjpeg-turbo, spng and libwebp, and
sharp's come with libvips: hand-tuned C with SIMD. Pixels' are younger. Its
WebP encoder is the slowest stage, and most of the gap on the WebP workload
comes from it.

Peak memory on many concurrent PNG decodes is higher than the others': Pixels'
decoder holds it, not the runtime.
