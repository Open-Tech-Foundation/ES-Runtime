# esdev start

```sh
esdev start
```

It is [`esdev build`](/docs/esdev/build) on a loop. A dev build differs from a
release build in three ways and no more: `process.env.NODE_ENV` is
`"development"`, nothing is content-hashed, and the browser bundle is built so a
module can be replaced in place. Dev and prod disagreeing about how a module
*resolves* is the failure this toolchain exists to prevent, and none of the three
touches that.

On a change: rebuild, restart the server if its bundle moved, and patch the page
— or reload it, if nothing accepted the change.

## The server is yours

```json
"start": { "run": "server" }
```

That names the target whose output *is* your server. esdev runs it as a child
process under the config's `permissions` and restarts it with a `SIGTERM` — the
graceful stop production gets, so a request in flight when you save is answered
rather than dropped.

**It is the same file production runs.** No dev server stands in for it, nothing
wraps it, and there is no second code path that exists only on your machine.

A project with no server of its own — a static site, a single-page app — has
nothing to run, so esdev serves the output directory itself: files, an
`index.html` fallback for client-side routes, and nothing else.

## A failed build changes nothing

```text
esdev: src/App.tsx: Unexpected token
```

The server you were about to fix it on is still running, still serving, and the
browser is not told anything. A syntax error mid-edit is the most ordinary event
in a dev loop; it should cost you a message.

The rebuild happens **before** anything is stopped, so the old server also
answers *during* it.

## The update channel

Every built document gets a few lines that open a WebSocket to
`ws://127.0.0.1:<port>/@esdev/hmr` and act on what arrives — a module patch, a
stylesheet swap, or a reload. It is esdev's endpoint rather than your
application's, so nothing dev-only reaches your source and the file you edit is
never written to.

An update is sent **after** a restart finishes, so a page never fetches from a
server still coming back up. The client reconnects on its own, backing off to a
5 s ceiling, because a restarted dev server is the ordinary case.

## Options

| | |
| --- | --- |
| `--port=<n>` | The port you open |
| `--config=<path>` | Read this instead of `./esdev.json` |
| `--shutdown-grace=<ms>` | How long the server may drain on a restart |

```json
"start": { "run": "server", "watch": ["server", "web"], "serve": "dist", "port": 8080 }
```

`watch` narrows what gets rebuilt; leaving it out rebuilds everything, which is
what you want at 40 ms a build. `serve` overrides the directory served when
there is no `run`.

## The port

`--port` is the port you open. With a `run` target that is your server's; without
one esdev serves the output, so it is esdev's.

A port you name is a promise and fails if it is taken. One you do not name takes
what your `listen` grant says, or a free one, and prints where it went:

```text
esdev: 8080 was taken; use --port to pin one
esdev: the app is on http://localhost:33407
```

Your server's port moves only when the project has said enough for the move to be
safe, and both halves are grants you already write:

```json
"permissions": { "allow": { "listen": ["8080"], "env": ["PORT"] } }
```

One port, so there is one to move — and `PORT`, so the server can be told which
one it got. The rewritten grant is the same capability with a different number,
so development still runs under the deployment's grant. A project shaped any
other way is left alone, which is what lets two of them run at once.

## Hot module replacement

A changed module is patched into the running page instead of reloading it, so
scroll position, open dialogs and half-filled forms survive a save. `--no-hot`
opts out.

It is not tied to a framework. A module opts in with `import.meta.hot`:

```js
import { render } from "./view.js";

render();

import.meta.hot.accept();
```

If nothing on the way up accepts a change, the page reloads.

### The API

| | |
| --- | --- |
| `accept()` | Re-run this module in place |
| `accept(cb)` | …and call `cb(newExports)` after |
| `accept(dep, cb)` | Re-run **that dependency** and call `cb(itsNewExports)` |
| `accept([deps], cb)` | The same, for several |
| `signal` | `AbortSignal`, aborted just before this module is replaced |
| `keep(key, make)` | Made once, returned on every replacement after |
| `dispose(cb)` | Runs before replacement, with `data` |
| `data` | An object that survives replacement |
| `decline()` | Refuse replacement — any change reaching here reloads |
| `invalidate()` | Hand the update up to this module's importers |

`import.meta.hot` is `undefined` in a production build, so `if (import.meta.hot)`
is how a module says "dev only" and still typechecks.

### Cleanup, without cleanup code

`signal` is aborted just before your module is replaced. Anything that takes one
tears itself down:

```js
addEventListener("resize", onResize, { signal: import.meta.hot.signal });
```

That line is also correct in production, where the signal is never aborted. For
APIs that do not take a signal:

```js
const timer = setInterval(tick, 1000);
import.meta.hot.signal.addEventListener("abort", () => clearInterval(timer));
```

### State across replacements

```js
const cache = import.meta.hot.keep("cache", () => new Map());
```

Made once, returned every time after — one call site, where `dispose` + `data`
is two that have to agree.

### React

Already wired up in the react template: edit a component and it re-renders with
its `useState` intact. It is React Fast Refresh, turned on by `"refresh": "react"`
on the target:

```json
"web": { "entry": "index.html", "outdir": "dist", "refresh": "react" }
```

Under it, the refresh is an ordinary `accept` callback — a framework with its own
scheme writes its own pass rather than esdev learning about it.

### Another framework's scheme

`"react"` is the one esdev implements, and it used to be the only name the
config would take — so every other framework got a full page reload on each
edit, not because the mechanism was missing (`import.meta.hot` is the same for
everyone) but because the target had no way to say it had a scheme.

Name yours, and write the per-module half as a
[plugin](/docs/esdev/plugins) — a `transform` against the same contract
`react-refresh` uses:

```json
{
  "plugins": ["./plugins/otfw-refresh.js"],
  "targets": { "web": { "entry": "index.html", "outdir": "dist", "refresh": "otfw" } }
}
```

A name esdev does not implement is accepted when the target has plugins and
**refused** when it has none — where nothing could implement it, the name can
only be a typo, and a `refresh` that silently did nothing is a project whose
components stop keeping their state one day with the reason sitting unread in a
config file.

<Callout type="note" title="What it costs">
  Dev mode turns treeshaking off, so the react template's dev bundle goes from
  870 KB to 1.45 MB and a rebuild costs ~20 ms more. Development only — nothing
  you ship changes.
</Callout>

## What is watched

The project root, minus `node_modules`, `.git`, `dist`, `target`, `.cache` and
**every directory your targets write into** — a build that triggered itself
would never settle. Ignored names are matched below the root, so a project
living in a directory called `target` is still watched.

Modules, and the things a *build* consumes that a run does not: `index.html`,
stylesheets, images, fonts.
