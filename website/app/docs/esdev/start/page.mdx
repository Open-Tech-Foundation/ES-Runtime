# esdev start

```sh
esdev start
```

It is [`esdev build`](/docs/esdev/build) on a loop. A dev build differs from a
release build in **two ways** — `process.env.NODE_ENV` is `"development"`, and
nothing is content-hashed — and in nothing else. Dev and prod disagreeing about
how a module resolves is the failure this toolchain exists to prevent.

On a change: rebuild, restart the server, tell the browser.

## The server is yours

```json
"start": { "run": "server" }
```

That names the target whose output *is* your server. esdev runs it as a child
process under the config's `permissions` and restarts it with a `SIGTERM` — the
graceful stop production gets, so a request in flight when you save is answered
rather than dropped.

**It is the same file production runs.** No dev server stands in for it, nothing
wraps it, and there is no second code path that exists only on your machine.

A project with no server of its own — a static site, a single-page app — has
nothing to run, so esdev serves the output directory itself: files, an
`index.html` fallback for client-side routes, and nothing else.

## A failed build changes nothing

```
esdev: src/App.tsx: Unexpected token
```

The server you were about to fix it on is still running, still serving, and the
browser is not told anything. A syntax error mid-edit is the most ordinary event
in a dev loop; it should cost you a message.

The rebuild happens **before** anything is stopped, so the old server also
answers *during* it.

## The update channel

Every built document gets a few lines that open a `WebSocket` against
`ws://127.0.0.1:<port>/@esdev/hmr` and act on what arrives. It is esdev's
endpoint, not your application's — nothing dev-only ends up in your source, and
the file you edit is never written to.

Today one message crosses it, `{"type":"reload"}`, and the page reloads. It is a
socket rather than the event stream it used to be because of what it is being
built to carry: a hot update is a module's source, which is multi-line
JavaScript that a line protocol would have to re-encode on every save — and an
event stream runs out of connections at about six tabs of one origin, after
which the seventh silently stops updating.

What that cost is a reconnect loop, which `EventSource` used to provide for
free. The injected client backs off from 250 ms to a 5 s ceiling, because a dev
server being restarted is the ordinary case rather than a failure.

The message is sent **after** the restart. A page told to reload while the
server is still coming back gets a connection refused and stays blank.

<Callout type="note" title="Full reload, not HMR">
  Nothing is preserved across it — your form, your open modal, your scroll
  position all reset. What buys that back is hot module replacement, which needs
  a transform callable from JavaScript, and esdev has none yet.
</Callout>

## Options

| | |
| --- | --- |
| `--port=<n>` | The port you open |
| `--config=<path>` | Read this instead of `./esdev.json` |
| `--shutdown-grace=<ms>` | How long the server may drain on a restart |

```json
"start": { "run": "server", "watch": ["server", "web"], "serve": "dist", "port": 8080 }
```

`watch` narrows what gets rebuilt; leaving it out rebuilds everything, which is
what you want at 40 ms a build. `serve` overrides the directory served when
there is no `run`.

## The port

There is one, and it is the one you open. When your project runs a server of its
own that is *your server's* port; when it does not — a static site, a single-page
app — esdev is what you open, so it is esdev's.

**One you named is a promise** and fails if it is taken. **One you did not is a
convenience** — it takes the port your `listen` grant names, or a free one if
that is busy, and prints where it went.

esdev's own endpoint on a fullstack project is not a port you deal with. It
carries one message to the page, the build writes its address into the page, and
it takes a free one. There is no flag for it because there is nobody to type
one.

```
esdev: 8080 was taken; use --port to pin one
esdev: the app is on http://localhost:33407
```

Your server's port moves only when the project says enough for the move to be
safe, and both halves are grants you were already writing:

```json
"permissions": { "allow": { "listen": ["8080"], "env": ["PORT"] } }
```

One port and no more, so there is a port to move — and `PORT`, so the server can
be told which one it got. The rewritten grant is the same capability with a
different number, never a wider one, so development still runs under the
deployment's grant. A project shaped any other way is left exactly as it is.

That is what lets two projects be in development at once without either of them
being about a number nobody chose.

## What is watched

The project root, minus `node_modules`, `.git`, `dist`, `target`, `.cache` and
**every directory your targets write into** — a build that triggered itself
would never settle. Ignored names are matched below the root, so a project
living in a directory called `target` is still watched.

Modules, and the things a *build* consumes that a run does not: `index.html`,
stylesheets, images, fonts.
