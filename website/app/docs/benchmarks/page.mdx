# Benchmarks

Standard Web APIs, the same script on each runtime (n/a where a runtime lacks one). Lower is better.

**Runtimes measured**

<RuntimeVersions />

<Callout type="info" title="How it's measured">
  - Runtimes run **interleaved, in randomized order** each repetition — one shared contention window.
  - Each cell is the **minimum** over repetitions (the contention-free floor), after a discarded warmup.
  - High-variance cells are flagged in the raw output.
</Callout>

## Hashing

`crypto` above is async `crypto.subtle`; these rows are what the caller wanted — encoded hashes, synchronously. [`runtime:hashing`](/api/hashing) on esrun, `Bun.CryptoHasher`, `node:crypto` elsewhere; `hash_fast` only exists on esrun and Bun.

<BenchChart group="hashing" />

<Callout type="note" title="Same work, two pipelines">
  `hash_hex` and `sha256` are the **same work** — 20 000 × SHA-256 of one 4 KiB
  buffer — async vs sync (esrun 7% apart, Node 3.2×: `crypto.subtle` here *is*
  the sync op with a resolved promise around it). The remaining ~2× is
  RustCrypto's portable Rust vs OpenSSL's AVX2 assembly — on SHA-NI hardware,
  which this box is not, it's a different measurement.
</Callout>

### Static files, measured externally

A 64 KiB file per response, external load generator on separate cores. Bun and Deno hand a file handle to the kernel; Node streams; esrun reads host-side.

<RpsChart server="staticserver" title="HTTP requests/sec · 64 KiB static file" />

<Callout type="warning" title="Two samples, not one table">
  Bare plain-text is the earlier sample, Hono JSON the 2026-10-01 refresh —
  compare down a column, never across it. Higher is better.
</Callout>

| Runtime | Bare server req/sec | Through Hono req/sec |
| --- | ---: | ---: |
| Deno | 85,070 | 69,741 |
| Bun | 82,615 | 73,951 |
| esrun | 49,537 | 50,601 |
| Node | 29,558 | 30,872 |

The Hono column serves `{"message":"Hello, World!"}` through unmodified npm ESM off `node_modules` — esrun at 50,601 req/s against Bun's 73,951.

esrun, Bun and Deno each saturate ~one core here — a per-request gap, not a core-count one. The stable measure is server CPU time per request:

| Server | CPU µs/req | ~req/s on 1 core |
| --- | ---: | ---: |
| Bare hyper, no JS (transport floor) | ~10.4 | — |
| Deno | ~11.9 | ~84k |
| Bun | ~12.2 | ~82k |
| esrun | ~18.2 | ~55k |
| Node | ~33.8 | ~30k |

<Callout type="note" title="The ~8µs seam">
  Bun/Deno add ~2µs of JS-handler overhead over bare hyper; esrun adds ~8µs —
  the injectable-provider + driven-loop seam, tuned from ~29µs via batched
  accept, structured metadata, lazy bodies/headers, and the host-validated URL.
</Callout>

## Redis clients

esrun with [`@opentf/esrun-redis`](/docs/db/redis) against Bun's built-in client and **both** npm clients (`redis` and `ioredis`) on Node and Deno — they don't perform alike, so one can't stand in for the other.

Wall ms, **min of 5**, lower is better. Checksums agreed on all five workloads.

| Workload | esrun | Node<br/>node-redis | Node<br/>ioredis | Bun<br/>built-in | Deno<br/>node-redis | Deno<br/>ioredis |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| `serial_set` — 5 000 `SET`, one at a time | 858 | 1029 | 910 | <Win>666</Win> | 1030 | 886 |
| `serial_get` — 5 000 `GET`, one at a time | 854 | 1040 | 884 | <Win>645</Win> | 1032 | 873 |
| `pipeline` — 20 000 `SET` in one batch | 225 | 374 | 203 | <Win>72</Win> | 366 | 186 |
| `list` — `LRANGE` over 50 000 elements | 158 | 203 | 119 | <Win>28</Win> | 209 | 111 |
| `hash` — 200 × `HGETALL` of 1 000 fields | 957 | 479 | 496 | <Win>205</Win> | 459 | 494 |

Peak RSS, MB:

| Workload | esrun | Node<br/>node-redis | Node<br/>ioredis | Bun<br/>built-in | Deno<br/>node-redis | Deno<br/>ioredis |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| `serial_set` | 38.4 | 112.3 | 79.1 | <Win>33.6</Win> | 124.4 | 99.6 |
| `serial_get` | 38.8 | 112.9 | 79.6 | <Win>34.0</Win> | 123.5 | 99.2 |
| `pipeline` | 123.8 | 181.1 | 129.1 | <Win>44.3</Win> | 191.6 | 139.5 |
| `list` | 92.9 | 96.1 | 86.5 | <Win>40.7</Win> | 103.8 | 86.7 |
| `hash` | 78.7 | 101.4 | 97.2 | <Win>45.0</Win> | 114.1 | 113.7 |

<Callout type="tip" title="Where esrun wins">
  Fastest where the **round trip** dominates (858 ms vs 1029/910) at a third of
  the memory (38 vs 79–124 MB) — and ahead of node-redis on batch and list.
  Bun's native C++ leads everything: 1.3× on round trips, 3–5× on decode.
</Callout>

<Callout type="info" title="The hash gap, isolated">
  957 ms vs ~480 on repeated `HGETALL` — the **map** path only, not decoding
  (list scan is mid-pack) and not UTF-8 (`binary: true` was 2% faster). A RESP3
  map crosses as a pair array of wrapper objects holding copied `Uint8Array`s
  — ~4 allocations per field — where ioredis builds the same object twice as
  fast. Fixable implementation cost.
</Callout>

Unlike the rest of this page, these runs are **not interleaved** — treat small gaps as noise. Reproduce with `bench/db/redis/run.sh`.

## SQLite

esrun's [`runtime:db`](/docs/db) (async, Turso 0.8.3) against synchronous in-process SQLite: `node:sqlite` on Node and Deno, `bun:sqlite` on Bun. Same schema, same rows, agreeing checksums.

Wall ms, **min of 5**, lower is better.

| Workload | esrun | Node | Bun | Deno |
| --- | ---: | ---: | ---: | ---: |
| `open` — fresh file + schema | 26.3 | 33.0 | <Win>11.6</Win> | 30.9 |
| `insert` — 50 000 rows, one statement each | 1198.4 | 187.3 | <Win>146.8</Win> | 204.1 |
| `insert_many` — the same 50 000 in one batch | 391.1 | n/a | n/a | n/a |
| `scan_num` — full scan, 3 numeric columns | 41.4 | 98.5 | <Win>22.1</Win> | 123.8 |
| `scan_text` — full scan, 2 text columns | 52.1 | 91.5 | <Win>25.5</Win> | 118.0 |
| `point` — 5 000 lookups by id | 162.5 | 81.4 | <Win>52.1</Win> | 76.0 |
| `stream` — 200 000-row scan through the cursor | 77.9 | 201.9 | <Win>47.6</Win> | 312.9 |

Peak RSS, MB:

| Workload | esrun | Node | Bun | Deno |
| --- | ---: | ---: | ---: | ---: |
| `open` | 36.2 | 46.8 | <Win>18.5</Win> | 36.0 |
| `insert` | 64.3 | 59.5 | <Win>44.5</Win> | 52.3 |
| `insert_many` | 149.6 | n/a | n/a | n/a |
| `scan_num` | 53.9 | 59.7 | <Win>35.7</Win> | 57.8 |
| `scan_text` | 55.4 | 59.6 | <Win>41.3</Win> | 57.2 |
| `point` | 47.3 | 50.2 | <Win>27.5</Win> | 41.3 |
| `stream` | 61.9 | 65.4 | <Win>41.0</Win> | 64.9 |

<Callout type="tip" title="Batch the writes">
  Per-statement crossings are esrun's cost — 1198 ms for 50 000 single-row
  `execute`s vs ~150–200 sync — and `insert_many` is the answer: one crossing,
  391 ms. The streaming scan lands second (78 vs 202/313); only `point`
  lookups lose outside the boundary (163 vs 52–81).
</Callout>

<Callout type="info" title="What runs where">
  One shared definition (`bench/db/workload.mjs`); `insert_many` is esrun-only,
  the sync APIs have no equivalent. Memory is mid-pack except the batch, which
  holds all rows in JS up front.
</Callout>

Unlike the rest of this page, these runs are **not interleaved** — treat small gaps as noise. Reproduce with `bench/db/run.sh`.

## Reproduce

The harness lives in `bench/`, auto-detects runtimes, and emits the JSON behind these charts:

```sh
# human-readable table
bench/run.sh

# one section only — see `bench/run.sh --list`
GROUP=fs bench/run.sh

# regenerate the data module this page renders
bench/gen-bench-data.sh

# one section, or a few rows, merged into the rest
SECTIONS=rps_sustained bench/gen-bench-data.sh
bench/gen-bench-data.sh regex strings

# just the HTTP/1.1 vs HTTP/2 table
bench/http2.sh
```

<Callout type="tip" title="Your hardware, your numbers">
  Numbers vary by machine — treat them as relative, not absolute. For CLI/script
  benchmarking, `hyperfine` is also a good fit.
</Callout>
