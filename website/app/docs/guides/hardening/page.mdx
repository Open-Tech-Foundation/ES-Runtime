# Securing a run

`esrun app.js` grants every capability. That is the right default for a script
you just wrote and are about to run yourself; it is the wrong default for
anything with dependencies, a network, or a production deployment.

This guide is the practical path from one to the other. It is a **method**, not
a list of flags to copy: start from nothing, run it, and grant back exactly what
breaks. The [security model](/docs/security) explains *why* it works this way;
the [CLI reference](/api/cli#permissions) is the complete flag list.

## The method

<Callout type="tip" title="Grant back, never take away">
  Do not start from a working command and remove flags — you will stop the
  moment it runs, which is before you have found what it *doesn't* need. Start
  from `--deny-all`, where nothing works, and add until it does. What you end up
  with is the honest minimum.
</Callout>

### 1. Start from nothing

```sh
esrun --deny-all server.js
```

Under `--deny-all` a run can compute and nothing else. It still executes the
entry file — that file is read before the runtime exists, and you named it — but
it cannot read a second file, import a package, reach the network, or see the
environment.

The first thing that breaks tells you what to grant:

```
NotAllowedError: capability denied: FileSystem (permission "imports")
```

The message names the flag word in parentheses. `permission "imports"` →
`--allow-imports`.

### 2. Grant capabilities back

Repeat until the program starts. For a typical HTTP service:

```sh
esrun --deny-all --allow-imports --allow-listen --allow-net --allow-env \
      --allow-read server.js
```

This already excludes a great deal — no `--allow-write`, no `--allow-run`, no
`--allow-signals` — but each grant it *does* carry is still whole. `--allow-net`
at this stage means "any host on the internet".

### 3. Narrow each grant to a list

Seven of the eight names take a comma-separated list. Now go back through the
command and replace each grant with what the service actually touches:

```sh
esrun --deny-all --allow-imports \
      --allow-listen=8080 \
      --allow-net=db.internal:5432,api.stripe.com \
      --allow-env=PORT,DATABASE_URL,STRIPE_KEY \
      --allow-read=./public,./config \
      --allow-write=./var/log \
      --allow-signals=SIGTERM \
      server.js
```

That command is now a readable statement of everything the service may touch,
and it is enforced. Commit it next to the code — a diff that widens it is a diff
worth reviewing.

<Callout type="note" title="--allow-net is the one that stops an exfiltration">
  A compromised dependency does not need a new capability to steal your data. It
  has the network access your application legitimately needs. Narrowing `net` to
  the two hosts you actually call is what turns that into a refusal — and the
  check runs on **every redirect hop**, so a `302` toward a denied host fails
  rather than being followed.
</Callout>

## Reading a denial

Three different refusals mean three different fixes. The error code tells you
which:

| Code | Means | Fix |
| --- | --- | --- |
| `ERR_CAPABILITY_DENIED` | The capability was never granted | Add `--allow-<name>` |
| `ERR_PERMISSION_DENIED` | Granted, but not for *this* value | Add the value to that flag's list |
| `ERR_JAIL_ESCAPE` | Outside the project root entirely | Not a flag — move the file, or run from a root that contains it |

What they look like:

```
NotAllowedError | ERR_CAPABILITY_DENIED | capability denied: Net (permission "net")
Error           | ERR_PERMISSION_DENIED | example.com:443 is not an allowed address (fetch)
Error           | ERR_PERMISSION_DENIED | /srv/app/secret.txt is not an allowed path (read)
Error           | ERR_JAIL_ESCAPE       | path /etc/passwd escapes the filesystem root jail /srv/app
```

<Callout type="note" title="A scoped grant is still a grant">
  `--allow-net=api.stripe.com` reports `permissions.has("net") === true`. The
  capability is what opens the door; the list is what the provider then declines
  to hand over. That is why the two codes are distinct — "you never had `net`"
  and "you have `net`, but not for that host" are different bugs in your
  deployment command.
</Callout>

## Bound what may load

Capabilities bound what running code may *reach*. Which modules may **become**
running code is a separate question, with a separate mechanism — a JSON file:

```sh
esrun --deny-all --allow-imports --import-policy=./import-policy.json server.js
```

```json
{
  "allow": ["./src", "express", "@acme/ui"],
  "deny": ["aws-sdk"]
}
```

A denied import fails to load, by name:

```
module loading failed: package aws-sdk is denied by the import policy
```

Entries beginning with `.` or `/` are paths covering their subtree; everything
else is a package name. **Deny wins over allow**, and omitting `"allow"` permits
everything not denied — the shape to reach for first, since a deny-only policy
is something you can adopt on an existing project today. See the
[full rules](/api/cli#import-policy).

<Callout type="warning" title="A policy names packages, not content">
  `"express"` says the loader may resolve that package. It says nothing about
  which version, or whether the bytes are the ones you audited. Keep your
  lockfile — it is the install-time half of this, and the policy does not
  replace it.
</Callout>

## Two things worth refusing outright

<Callout type="danger" title="Don't grant Run">
  A child process runs **outside** every confinement here — no capability check,
  no root jail, no execution deadline reaches it. `--allow-run=git` is a bound on
  *which* program, not on what that program may then do, and granting `Run` at
  all to code you don't trust grants everything the host user can do. If you need
  it, name the program, and treat the grant as the sandbox boundary it is.
</Callout>

<Callout type="danger" title="Don't grant env wholesale">
  `--allow-env` hands over every variable in the process — including the ones
  belonging to your CI runner, your cloud metadata, and every other service on
  the box. `--allow-env=PORT,DATABASE_URL` makes every other variable **absent**,
  so guest code can neither read one nor learn that it exists.
</Callout>

## Secrets

A `.env` file is never discovered on its own; it loads only when `--env-file`
names it, and loaded values fill unset keys rather than overriding the real
environment.

```sh
esrun --env-file=.env.production --deny-all --allow-env=PORT,DATABASE_URL app.js
```

Keys ending in `_KEY` / `_TOKEN` / `_SECRET` / `_PASS(WORD)`, or containing
`CREDENTIAL` / `AUTH`, become [`Secret`](/api/process) values that print as
`[redacted]` in logs and JSON.

<Callout type="danger" title="Masking is for accidents, not attackers">
  Guest code can call `unmask()` itself. Masking keeps a token out of a log line
  and a stack trace; it is not a confinement. The confinement is
  `--allow-env=<names>` — a variable that was never in the snapshot cannot be
  unmasked.
</Callout>

## A pre-deploy checklist

- The command starts with `--deny-all`, not with `--deny-<name>`.
- Every `--allow-` flag that can carry a list carries one.
- `--allow-run` is absent, or names exactly one program you can defend.
- `--allow-env` names variables; it is not bare.
- `--allow-write` names the narrowest directory that works — logs and a temp
  directory, not the project root.
- `--allow-net` names hosts, and you have checked it against what the app calls
  on its *error* paths too (retries, telemetry, crash reporters).
- An `--import-policy` exists, even if it only denies.
- The deployment command is committed and code-reviewed like source.

## What this does not cover

Worth knowing before you rely on it:

- **Integrity.** Nothing here verifies that a package is the code you audited —
  only which packages and paths may load. Lockfiles remain your install-time
  control.
- **Resource limits.** Capabilities bound reach, not consumption. A denied
  script still computes; use `--timeout` for a wall-clock bound and your
  supervisor (container limits, cgroups) for CPU and memory.
- **Runtime revocation.** The policy is fixed at launch. There is no `.drop()` —
  a program cannot narrow its own grants partway through, and cannot widen them
  either.
- **The host user.** Everything here confines the JavaScript. Run the process as
  an unprivileged user in a container regardless; this is a layer, not a
  replacement for the ones below it.
