# PostgreSQL types

What [`@opentf/esrun-postgres`](/docs/db) turns each PostgreSQL type into, next
to the drivers people arrive from. Every cell was produced by running the same
query through each driver — the scripts are in `bench/db/pg/types-*.mjs`, so
this table can be regenerated rather than trusted.

<Callout type="info" title="The text and binary paths agree">
  The driver asks for the binary wire format where it is cheaper to read, and
  text where it is not — but a wire format is how a value travels, not what it
  is. All twenty-one columns below decode identically either way, and a test
  reads the same row through both paths and requires every column to match.
</Callout>

## Where this driver differs, and why

**`int8` is a number, or a `bigint` when it has to be.** The other drivers
return a string, which is exact but unusable without converting it first — and
converting it with `Number()` is precisely the precision loss the string was
avoiding. Here a value that fits a `number` is one, and a value that does not is
a `bigint`, so it is exact *and* arithmetic works.

**Dates and times are Temporal.** A `Date` is an instant with millisecond
resolution, which makes it the wrong type for three of these columns at once:

- it cannot hold the microseconds a `timestamp` has — every other driver in that
  table answers `.123` for a column containing `.123456`;
- it has no way to express `timestamp without time zone` except by inventing a
  zone, and the drivers disagree about which. `postgres.js` reads it in the
  *client's* zone, so the same column comes back differently depending on the
  machine; `bun:sql` reads it as UTC;
- a `date` is a calendar day, not an instant, and `Date` can only be an instant
  — which is why the others return midnight UTC and hope.

`Temporal.Instant`, `PlainDateTime`, `PlainDate`, `PlainTime` and `Duration` say
exactly what each column is, and keep the microseconds.

<Callout type="warning" title="Opting out">
  `connect(url, { temporal: false })` restores the older mapping — `Date` for
  timestamps, strings for dates, times and intervals — for code that has to hand
  a `Date` to something that expects one. The two wire formats agree in that
  mode too.
</Callout>

**`numeric` stays a string** in every driver here, and should. It is arbitrary
precision by definition, and a double is the one representation guaranteed to
lose it — a column chosen for exactness should not be rounded on the way out.

## Notes on the rest

- **Arrays** decode into JavaScript arrays, nested and null-aware. An unquoted
  `NULL` is the null element; a quoted `"NULL"` is four characters.
- **An array of a type this driver does not decode** comes back as its raw
  literal, because the wire does not say a column *is* an array — `int4[]`
  reports OID 1007 and nothing more — so it cannot be told from a text column
  containing braces.
- **`bytea`** is a `Uint8Array`. In the binary format those are the bytes as
  sent; text sends hex, which doubles the size and is parsed back.
- **`interval`** keeps months, days and time separate, as PostgreSQL stores
  them and as `Temporal.Duration` represents them — a month is not thirty days,
  and flattening it would decide something the value did not say.

## Regenerating this table

```sh
PG_URL=postgres://…  esrun bench/db/pg/types-esrun.mjs binary
PG_URL=postgres://…  esrun bench/db/pg/types-esrun.mjs text
PG_URL=postgres://…  node  bench/db/pg/types-postgresjs.mjs
PG_URL=postgres://…  bun   bench/db/pg/types-bunsql.mjs
```

Each prints `column<TAB>type value`, so the outputs diff directly.
