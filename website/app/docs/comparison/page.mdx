# esrun vs Node.js · Bun · Deno

Node.js, Bun, and Deno are general-purpose runtimes. esrun is narrower: a
secure, standards-first server runtime with deny-by-default permissions.
Dev tooling lives in [`esdev`](/esdev), never in production.

**Runtimes measured**

- esrun 0.38.0
- Node.js 24.21.0 (LTS)
- Bun 1.4.2
- Deno 2.9.7
- esdev 0.17.0 (development binary)

**Legend**

- <Yes /> Supported
- <Partial /> Partial / flagged / experimental
- <No /> Not supported

## Development binary (`esdev`)

TypeScript, JSX, CommonJS, bundling, tests and Tailwind live here — the
local-only binary. `esrun` runs the bundle; nothing below ships to production.

| Capability | esdev | Node.js | Bun | Deno |
| --- | :---: | :---: | :---: | :---: |
| TypeScript | <Yes /> | <Partial /> | <Yes /> | <Yes /> |
| JSX | <Yes /> | <No /> | <Yes /> | <Yes /> |
| CommonJS (require) | <Yes /> | <Yes /> | <Yes /> | <Yes /> |
| Bundler | <Yes /> | <No /> | <Yes /> | <Partial /> |
| Test runner | <Yes /> | <Yes /> | <Yes /> | <Yes /> |
| Tailwind CSS | <Yes /> | <No /> | <Partial /> | <No /> |
| Package installer | <No /> | <Yes /> | <Yes /> | <Yes /> |

**CommonJS** works because `esdev` converts packages to ES modules on first
import; `esrun` runs the bundle where that is already settled.

**TypeScript on Node** strips erasable syntax only — `enum` and `namespace`
need `--experimental-transform-types`.

**Bundler:** `deno bundle` works but warns it is experimental — hence <Partial />.

**Tailwind:** `esdev` compiles v4 with zero config ([docs](/esdev/build/tailwind));
Bun needs `bun-plugin-tailwind`; Node and Deno leave CSS to other tools.

**Package installer:** `esdev` has none by design — use your package manager.

## HTTP and networking

The server, the protocols it speaks, and the socket surface around it.

| Capability | esrun | Node.js | Bun | Deno |
| --- | :---: | :---: | :---: | :---: |
| Built-in HTTP server | <Yes /> | <Yes /> | <Yes /> | <Yes /> |
| HTTP/2 server (cleartext h2c + ALPN) | <Yes /> | <Yes /> | <Partial /> | <Yes /> |
| HTTP/3 server (QUIC) | <No /> | <No /> | <Partial /> | <No /> |
| Cookie parse / serialize API | <Yes /> | <No /> | <Yes /> | <Partial /> |
| Stalled-connection timeouts by default | <Yes /> | <Partial /> | <Yes /> | <No /> |
| UDP datagram sockets | <Yes /> | <Yes /> | <Yes /> | <Yes /> |
| UDP multicast join/leave | <Yes /> | <Yes /> | <Yes /> | <Yes /> |
| Connected UDP sockets | <Yes /> | <Yes /> | <Yes /> | <Yes /> |

**On the HTTP/2 row.** esrun and Deno serve both versions from one `serve()`;
Node needs a separate `node:http2` server, and Bun only via `node:http2` —
its own `Bun.serve` is HTTP/1.1-only. Throughput: [Benchmarks](/docs/benchmarks#http2).

**On the stalled-connection row.** Measured: esrun, Bun and Node close a
connection that sends nothing; Deno holds it open. Node is <Partial /> — its
60s `headersTimeout` on a 30s check lets one linger ~90s. Per-runtime times:
[HTTP server comparison](/docs/internals/http/comparison).

**On the HTTP/3 row.** Only Bun serves it (experimental, hence <Partial />).
No `node:quic` on Node LTS; Deno 2.9 exposes no QUIC API at all. QUIC is a
new UDP transport with its own TLS stack — a new listener, not a flag — so
esrun has none yet.

**On the cookie row.** esrun and Bun ship `Cookie`/`CookieMap`; Deno's is a
stdlib package, Node has none. Unlike Bun's, esrun's **throws** on cookies a
browser would drop (`SameSite=None` without `Secure`, `__Host-` with `Domain`).
See [Cookies](/docs/http/basics#cookies).

**On the UDP rows.** All four have it. Deno's stable path is `node:dgram`;
Bun's surface is widest (`sendMany`, source-specific membership); esrun's is
the only one where binding and sending are **separate grants**. Call-by-call
mapping: [UDP guide](/docs/guides/udp#coming-from-node-deno-or-bun).

**On the database rows.** `postgres` and `mysql` live in `runtime:db`; Redis

drivers to npm.

over `runtime:net`. Elsewhere mail is npm,
where `nodemailer` needs `node:net`, which esrun lacks.

**On the image-processing row.** Node has no image API; Deno encodes PNG/JPEG
only. Per-operation breakdown: [Images, feature by feature](#images-feature-by-feature).

## Workers, state and observability

Concurrency, isolation between workers, durable state, and self-exports.

| Capability | esrun | Node.js | Bun | Deno |
| --- | :---: | :---: | :---: | :---: |
| Workers / multi-thread | <Yes /> | <Yes /> | <Yes /> | <Yes /> |
| Per-worker memory limit | <Yes /> | <Yes /> | <No /> | <Yes /> |
| Per-worker capabilities | <Yes /> | <No /> | <No /> | <Partial /> |
| `worker.unref()` | <Yes /> | <Yes /> | <Yes /> | <Yes /> |
| Worker queue depth (backpressure signal) | <Yes /> | <No /> | <No /> | <No /> |
| Durable workers (addressable state, alarms) | <Yes /> | <No /> | <No /> | <No /> |
| Built-in OpenTelemetry export | <Yes /> | <No /> | <No /> | <Yes /> |

**On the worker rows.** Deno's web `Worker` has no `unref()` or memory limit
(`node:worker_threads` has both); Bun accepts `resourceLimits` but never
enforces it, per its own compatibility table.

**On the durable workers row.** Addressable instances with storage, alarms and
hibernating WebSockets — the Durable Objects model, self-hosted. The other
three leave state and scheduling to a database and job queue. See
[Durable workers](/docs/guides/durable-workers).

**On the OpenTelemetry row.** `esrun --otel` exports OTLP/HTTP spans with no
SDK; Deno (`OTEL_DENO=true`) also covers logs and metrics. Node and Bun need the
npm SDK; Bun's native tracing is unreleased.

## Security

The sandbox default and the flags that shape it. Full breakdown below in
[Permission models](#permission-models).

| Capability | esrun | Node.js | Bun | Deno |
| --- | :---: | :---: | :---: | :---: |
| Capability sandbox (deny by default) | <Yes /> | <Partial /> | <No /> | <Yes /> |
| Runtime permission flags (allow/deny) | <Yes /> | <Yes /> | <No /> | <Yes /> |

**On the permission row.** This is the *CLI*; the sandbox row above is the
**default**. Both esrun and Deno deny by default — the table below shows how
differently they grant, scope and query.

> **esrun sandbox in one line:** `esrun app.js` holds nothing — `--allow-*`
> names what a run may reach. `esdev` grants everything, so no flags indoors.

## Node.js compatibility

esrun runs standards-only code — no `node:` builtins, FFI, or native addons.
Porting means leaving those behind: [From Node.js](/docs/migration/node).

| Capability | esrun | Node.js | Bun | Deno |
| --- | :---: | :---: | :---: | :---: |
| Node.js compatibility (`node:` builtins) | <No /> | <Yes /> | <Partial /> | <Partial /> |
| FFI (dlopen) | <No /> | <No /> | <Yes /> | <Yes /> |
| Native addons (N-API) | <No /> | <Yes /> | <Yes /> | <Yes /> |

**On these rows.** Node LTS has no `node:ffi` at all; Bun (`bun:ffi`) and
Deno (`Deno.dlopen`) do. Both report incomplete `node:` coverage (Bun lists partial modules, Deno passes 75%+ of
Node's suite).

## Permission models

| | esrun | Node.js | Bun | Deno |
| --- | --- | --- | --- | --- |
| Restricted by default | <Yes /> | <No /> | <No /> | <Yes /> |
| Turned on by | always on (`-A` off) | `--permission` | — | always on (`-A` off) |
| Direction | allow-list, or `--allow-all` + `--deny-*` | allow-list | — | allow-list + `--deny-*` |
| Scoped to paths / hosts | <Yes /> | <Yes /> | — | <Yes /> |
| Interactive prompt | <No /> | <No /> | — | <Yes /> |
| Entry file readable | <Yes /> | <Yes /> | — | <Yes /> |
| Local imports readable | `--allow-imports` | <No /> | — | <Yes /> |
| Allow/deny which modules load | `--import-policy` file | <No /> | — | <No /> |
| Query from JS | `permissions.has()` | `process.permission.has()` | — | `Deno.permissions.query()` |
| Drop privileges at runtime | <No /> | `.drop()` | — | `.revoke()` |
| Filesystem root jail | always on | <No /> | <No /> | <No /> |
| Status | alpha | stable (v22.13+) | [requested](https://github.com/oven-sh/bun/issues/6617) | stable |

- **Rows 6–8:** entry file runs, second file needs a grant (Deno exempts analysable imports). What the loader may *resolve* is separate: esrun's `--import-policy` (packages/paths) vs Deno's `--allow-import` (remote hosts); Node removed theirs.
- **Names:** `read`, `write`, `imports`, `net`, `listen`, `env`, `run`, `signals`, `workers`, `diagnostics`, `diagnostics-detail` — flags, `permissions.has()`, Worker options. See [Security model](/docs/security/permissions#granting-capabilities-in-esrun).

| | esrun<br/>`runtime:images` | Node.js<br/>sharp | Bun<br/>`Bun.Image` | Deno<br/>`createImageBitmap` |

### Speed

Full numbers: [Benchmarks](/docs/benchmarks#redis-clients). Bun's native client
leads (1.3× round trips, 3–5× decoding). Among JS clients esrun is fastest
where the round trip dominates at a third of the memory — but **2× slower on
repeated `HGETALL`**, a fixable map-decoding cost in this driver.

## Where the API surface differs

- **No Node.js API.** Only capability-gated `runtime:` modules — no `node:fs`,
  `Buffer`, or global `process`.
- **Globals are not host APIs.** Global scope stays Web-platform; no fs/process
  on globals either (like Deno, stricter).
- **Always-on filesystem jail.** Project-root confinement, symlink-proof, no
  off flag. `node_modules` walk stops at the run directory, not the fs root.
- **Two binaries.** `esrun` serves; `esdev` bundles, tests, watches, debugs.
  Same behavior core.
- **WASI is enforced, not advisory.** Preopen + capability + jail — Node's own
  docs call `node:wasi` not a secure sandbox. See [WebAssembly & WASI](/docs/wasm).

Status reflects general availability at the time of writing and is a summary, not
an exhaustive audit. See [Benchmarks](/docs/benchmarks) for measured performance.
