# esrun vs Node.js · Bun · Deno

Node.js, Bun, and Deno are general-purpose runtimes with broad toolchains and
(varying degrees of) Node.js compatibility. esrun is intentionally smaller: a
sandboxed, standards-only execution core you embed or run directly. The table
makes the trade-offs explicit.

| Capability | esrun | Node.js | Bun | Deno |
| --- | :---: | :---: | :---: | :---: |
| ES Modules | <Yes /> | <Yes /> | <Yes /> | <Yes /> |
| CommonJS (require) | <No /> | <Yes /> | <Yes /> | <Partial /> |
| TypeScript (built-in) | <No /> | <Yes /> | <Yes /> | <Yes /> |
| JSX (built-in) | <No /> | <No /> | <Yes /> | <Yes /> |
| JSON module imports | <Yes /> | <Yes /> | <Yes /> | <Yes /> |
| Web APIs (fetch/URL/streams/WebCrypto) | <Yes /> | <Yes /> | <Yes /> | <Yes /> |
| Built-in HTTP server | <Yes /> | <Yes /> | <Yes /> | <Yes /> |
| HTTP/2 server (cleartext h2c + ALPN) | <Yes /> | <Yes /> | <Partial /> | <Yes /> |
| Temporal API | <Yes /> | <Yes /> | <No /> | <Yes /> |
| WebAssembly | <Yes /> | <Yes /> | <Yes /> | <Yes /> |
| `.wasm` ES module imports | <Yes /> | <Yes /> | <No /> | <Yes /> |
| WASI preview 1 | <Yes /> | <Yes /> | <Partial /> | <Yes /> |
| Node.js compatibility (`node:` builtins) | <No /> | <Yes /> | <Yes /> | <Partial /> |
| Capability sandbox (deny by default) | <No /> | <Partial /> | <No /> | <Yes /> |
| Runtime permission flags (allow/deny) | <Yes /> | <Yes /> | <No /> | <Yes /> |
| Workers / multi-thread | <No /> | <Yes /> | <Yes /> | <Yes /> |
| FFI (dlopen) | <No /> | <No /> | <Yes /> | <Yes /> |
| Native addons (N-API) | <No /> | <Yes /> | <Yes /> | <Yes /> |
| Package installer | <No /> | <Yes /> | <Yes /> | <Yes /> |
| Bundler / test runner | <No /> | <Partial /> | <Yes /> | <Yes /> |
| Embeddable as a library | <Yes /> | <No /> | <No /> | <Partial /> |

**Legend:** <Yes /> Supported · <Partial /> Partial / flagged / experimental · <No /> Not supported

**On the HTTP/2 row.** esrun and Deno detect the version per connection on the
server they already have, so one `serve()` answers both. Node's h2c is a separate
API (`node:http2`); `node:http`'s server is HTTP/1.1-only. Bun is <Partial />
because it implements `node:http2` — which does serve h2c — while its own
`Bun.serve` is HTTP/1.1-only, so the flagship API and the HTTP/2 one are not the
same server. Measured throughput for all four:
[Benchmarks](/docs/benchmarks#http2).

**On the permission row.** It is about the *CLI*, and is a different question
from the sandbox row above it, which is about the **default**: esrun grants
everything by default and restricts on request, where Deno denies by default and
grants on request. Both have flags that allow or deny a capability, scopes that
narrow one to particular paths or hosts, and a way to ask from JS — the
[Permission models](#permission-models) table below breaks down how differently
they get there, and where esrun goes further (an always-on filesystem jail, and
a policy for what the module loader may resolve).

<br />

> **Note on the esrun sandbox column.** Deny-by-default applies to the
> **embeddable library**. The esrun **CLI** grants everything by default and
> restricts on request — see below.

## Permission models

| | esrun | Node.js | Bun | Deno |
| --- | --- | --- | --- | --- |
| Restricted by default | <No /> | <No /> | <No /> | <Yes /> |
| Turned on by | `--deny-all` | `--permission` | — | always on (`-A` off) |
| Direction | deny-list, or `--deny-all` + allow-list | allow-list | — | allow-list + `--deny-*` |
| Scoped to paths / hosts | <Yes /> | <Yes /> | — | <Yes /> |
| Interactive prompt | <No /> | <No /> | — | <Yes /> |
| Entry file readable | <Yes /> | <Yes /> | — | <Yes /> |
| Local imports readable | `--allow-imports` | <No /> | — | <Yes /> |
| Allow/deny which modules load | `--import-policy` file | <No /> | — | <No /> |
| Query from JS | `permissions.has()` | `process.permission.has()` | — | `Deno.permissions.query()` |
| Drop privileges at runtime | <No /> | `.drop()` | — | `.revoke()` |
| Filesystem root jail | always on | <No /> | <No /> | <No /> |
| Status | alpha | stable (v22.13+) | [proposed](https://github.com/oven-sh/bun/issues/26637) | stable |

Rows 6–7 are about the module graph: under esrun's `--deny-all` and Node's
`--permission`, the entry file still runs but a second file needs a grant. Deno
reads statically analysable imports without one.

Row 8 is a different question again — not *may the loader run* but *what may it
resolve*. esrun answers it outside the permission model, with a JSON
`--import-policy` file of allow/deny package names and paths. Deno's
similarly-named `--allow-import` is not this: it names which **remote hosts**
code may be fetched from, which esrun has no equivalent of because it refuses
remote modules outright. Node's module policy mechanism was deprecated and
removed.

esrun's eight denial names — `read`, `write`, `imports`, `net`, `listen`, `env`,
`run`, `signals` — are also what `permissions.has()` takes. See
[Security model](/docs/security#denying-capabilities-in-esrun).

## Where the API surface differs

- **No Node.js API.** Where Node.js, Bun, and Deno all expose `node:fs`,
  `Buffer`, and a global `process`, esrun exposes host functionality only through
  capability-gated `runtime:` modules.
- **Globals are not host APIs.** Like Deno, esrun keeps the global scope close to
  the Web platform — but it does not put filesystem or process access on a global
  either.
- **Always-on filesystem jail.** File access — including module resolution — is
  confined to a project root that can't be escaped, even via symlink, in both the
  library and the CLI, with no flag to turn it off. No other runtime here has an
  equivalent; their permission flags are the only confinement.
- **It embeds.** esrun is a Rust library with a driven event loop and no owned
  thread, designed to run inside a host application — a use case the others do not
  target.

- **WASI is enforced, not advisory.** Node's own docs say its `node:wasi` threat
  model "does not provide secure sandboxing". Here a guest's file access passes
  three independent checks — preopen, capability, root jail. See
  [WebAssembly & WASI](/docs/wasm).

Status reflects general availability at the time of writing and is a summary, not
an exhaustive audit. See [Benchmarks](/docs/benchmarks) for measured performance.
